# Clip

A clipboard manager for macOS that remembers what you copied, understands what
kind of thing it was, and keeps a small library of the text you reuse.

It is a menu-bar app. No Dock icon, no window until you ask for one, no account
required, and nothing leaves your Mac unless you turn on sync yourself.

![Clip's panel showing a clipboard history of text, prompts and an emoji](brand/screenshot-panel.png)

## What it does

### Remembers what you copied

Everything you copy is kept, recognised and filed. Clip works out what a clip
**is** rather than treating it all as text: plain text, code (with the language
detected), rich text, an emoji, an image, a video, a file, a folder, a URL, or a
color. URLs are recognised down to the service behind them, and Clip fetches the
page title so a link reads as what it points at.

Content marked confidential by the app that produced it is **never recorded**.
Password managers flag what they put on the pasteboard, and Clip honours that
flag by default, along with transient and auto-generated markers.

### A library, not just a history

Five kinds of thing live side by side, each with its own tab:

| | |
|---|---|
| **Clips** | Your history, newest first |
| **Prompts** | Text you reuse, with `{{variables}}` filled in when you paste |
| **Notes** | Written in a markdown editor |
| **Skills** | Markdown documents with front matter, for AI tooling |
| **Designs** | `DESIGN.md` design systems, which Clip can turn into app themes |

Plus colors, files and every other type as its own filter. Tabs are yours to
arrange: show, hide, reorder, and set the layout and density of each one
independently.

### Finds things fast

Search runs over everything at once - title, tags, body, source app, and the
date written the way you would say it, so "yesterday", "august" and "30/08" all
work. Three modes: contains, fuzzy and regular expression. Results are **ranked**
rather than merely filtered, so the document actually about typography comes
first when you search for typography.

Typing stays under 3 ms per keystroke against a 745-item library that includes
74 full design documents.

### Keyboard first

Open with a global shortcut (⌘⇧Space by default). Move with the arrow keys,
paste with Return, and reach every per-row action with ⌥→ without lifting your
hands. Any individual item can be given its own global shortcut, so the snippet
you paste forty times a day is one key away.

### Paste actions: the AI happens on the way out

The clipboard is the only thing on the machine that sees your work **in
transit**, and it knows both what you copied and where it is going. So Clip's AI
does not tidy your library - it finishes the text at the moment you paste it,
into the app you are already typing in.

**⌃⌥T pastes a translation.** Set two languages in Settings and one key goes
either way: Clip works out which of the two the text is in and gives you the
other. No menu, no round trip.

**⌃⌥A opens the action menu at the pointer**, from any app, with no panel on
screen. Translate to any configured language, rewrite in a style, improve a
prompt, fix grammar, shorten, turn into bullets, summarise, explain an error,
convert to JSON or a TypeScript type or a Swift struct, write a commit message,
write a reply, strip secrets - and any instruction of your own.

What this replaces: open a chat tab, paste, write an instruction, wait, select,
copy, switch back, paste. Eight actions and two context switches become one
keystroke.

Everything about the menu is yours: which actions are in it, their order (drag
to reorder), which languages and styles the submenus offer, and your own custom
actions with your own instructions. An action that is switched off is **absent**
from the menu rather than greyed out in it.

Both keys also work on the selected item while the panel is open.

**Rules that hold everywhere.** Every model call happens because you pressed
something - nothing on the capture path ever calls a model, so copying stays
instant, offline and free. A failed transform **pastes nothing and leaves your
clipboard exactly as it was**. Nine further actions work on a selected item in
the detail view - improve, proofread, title, tags, summarise, explain,
templatise, translate, build a theme - and each shows a diff before anything is
written.

Bring your own provider: Anthropic, OpenAI, Gemini, Ollama for local models, or
anything OpenAI-compatible. Keys live in the Keychain. Several can be configured
at once and given different roles.

### Things that need no model at all

- **Themes from a design document.** A `DESIGN.md` front-matter `colors:` block
  already is a theme. Clip reads it, maps the roles, and runs the result through
  a 43-pairing contrast audit, repairing what fails. Of a 74-document corpus, 65
  produce a theme that passes every pairing; the 9 that cannot say so plainly
  rather than shipping something unreadable.
- **A palette from a copied image**, by counting pixels.
- **Prompt variables**, remembered per name so the second use is usually Return.
- **Compose-paste**: mark several items, paste them as one block.

### Themes

Twelve built in, light and dark. Build your own, or generate one from a design
document or an image. Every theme is audited for contrast across 43 pairings
before it can be used, so a palette that looks good on a web page cannot ship
as an unreadable list.

### Sync, three ways, one at a time

1. **Sign in with Google.** Syncs through the project's own service. Simple, no
   setup. *(Unavailable in this open-source build - see below.)*
2. **Your own server**, connected with a token. Clip generates a complete PHP +
   MySQL setup kit: the code, a written config, and step-by-step instructions.
   Your data, your host, nobody else's.
3. **Export and import.** No server at all. Move a file between Macs.

Only one is active at a time, and switching is deliberate. Settings, themes and
tab arrangement sync too, on a cadence you choose from every minute to once a
day, or on quit.

> **On the open-source build:** the upstream app's sync service address is
> stripped from this repository. Publishing it would mean every fork syncing
> strangers into somebody else's database. Google sign-in therefore reports
> itself as unavailable here, and the other two methods work exactly as
> described. See [docs/SELF-HOSTING.md](docs/SELF-HOSTING.md) to run your own.

## Install

### From the DMG

Download `Clip-2.0.dmg`, open it, drag Clip onto Applications.

The first launch will say macOS cannot verify the developer. That is
expected, not a sign anything is wrong: Clip is free and open source, and
Apple charges $99 a year for the Developer ID certificate that would make
that warning go away. This project has chosen not to pay it. The warning
says nothing about whether the app is safe to run - it fires for every
unnotarised app regardless of what the app actually does. If you would
rather not take that on trust, the source is right here: read it, or build
it yourself with `./build.sh` or `./package.sh` below.

Two ways to open it anyway, both one-time:

- Right-click (or Control-click) Clip in Applications, choose **Open**, then
  confirm in the dialog that appears; or
- In Terminal: `xattr -dr com.apple.quarantine /Applications/Clip.app`, then
  open it normally.

Either way, you only do this once - macOS remembers the decision for that
build.

Clip will ask for **Accessibility** permission. It needs it to paste into other
apps and to register the global shortcut. It does not need, and does not ask
for, anything else.

### From source

```bash
git clone https://github.com/shaulv/Clip.git
cd clip
./build.sh            # builds and launches an unsigned Debug build
```

That is the whole setup. There is no package manager step, because there are no
packages: Clip links nothing but macOS frameworks.

```bash
./build.sh xcode      # open in Xcode instead
./package.sh          # build a signed Release and a .dmg
./package.sh --install   # ...and install it to /Applications
```

**The Xcode project is generated, not committed.** `regen-project.py` writes
`Clip.xcodeproj/project.pbxproj` from the files on disk. Add a Swift file
anywhere under `Clip/` and run it; there is no pbxproj to hand-edit and no merge
conflict to resolve in one. `build.sh` runs it for you.

### Where Clip keeps your data

Everything you have copied, every theme, tab and shortcut binding, lives in one
file: `~/Library/Application Support/Clip/clip.sqlite`. Saved images live
beside it in `Media/`. Your API keys and sync token are never in that folder -
they live in the macOS Keychain, under the service name `app.clip.ai`.

### Updating keeps everything

Installing a newer build over an older one - from a new DMG, `git pull` plus
`./build.sh`, or `./package.sh --install` - does not touch your history. On
every launch Clip checks that its database is readable (`PRAGMA quick_check`),
and before it changes anything for a new version it writes its own backup
(`clip.sqlite.backup-preupgrade-*`, right beside the database). If the file is
ever found damaged, Clip restores from the newest backup on its own and says
so; only if no backup can be restored does it stop and offer to pick one by
hand, rather than run empty and pretend nothing happened. Old installs
(`previous-versions/`) and old backups are kept for a while and then moved
into a dated `Reclaimed-*` folder - never deleted outright - and Settings >
Privacy > Storage lists anything currently reclaimable with a one-click
"Reclaim" button.

### Uninstalling

Deleting `Clip.app` removes the app only. Your history, themes and settings
stay in `~/Library/Application Support/Clip`, and your API keys and sync token
stay in the Keychain. To remove everything Clip has ever written:

1. Delete `Clip.app` (drag it to the Trash, or `rm -rf /Applications/Clip.app`).
2. Delete `~/Library/Application Support/Clip`.
3. Open **Keychain Access**, search for `Clip` or `app.clip.ai`, and delete
   the items it finds.

Reinstalling afterwards starts completely fresh. Reinstalling **without**
deleting step 2 first picks up exactly where you left off - that is the whole
point of keeping data and app separate.

## Testing

Clip is driven by a file-based harness rather than a UI-test framework: the
probe writes a command, the app performs it on the main thread exactly as a real
event would, and writes its observable state back out.

```bash
# Build the Testing configuration and start the app under it
xcodebuild -project Clip.xcodeproj -scheme Clip -configuration Testing \
  -derivedDataPath build-testing CODE_SIGNING_ALLOWED=NO build
CLIP_QA=1 CLIP_QA_SANDBOX=1 CLIP_HEADLESS=1 \
  ./build-testing/Build/Products/Testing/Clip.app/Contents/MacOS/Clip &

python3 qa-probe.py          # behaviour assertions; prints "N passed, N failed, N skipped"
python3 security-probe.py    # security checks; same summary line
python3 perf-probe.py        # timings and counters
```

Neither probe's pass/fail/skip count belongs in a doc: it is a run result,
not a fact about the code, and it changes with whatever you just touched. The
call-site totals above (how many assertions the suite is built from) do
belong here, which is why they are generated, not typed.

Three things about this harness are worth knowing before you add to it.

**It runs sandboxed.** `CLIP_QA_SANDBOX=1` moves the database, the media folder,
the Keychain service *and the preferences* somewhere else. A test cannot damage
the thing it is testing. Both halves of that were learned the hard way: a probe
once seeded into the live database, and later a different one left the user's
history limit set to 20.

**The harness is not in the shipped app.** It is compiled out unless
`CLIP_TESTING` is defined, which only the `Testing` configuration does. A bridge
that reads commands from a file and writes the whole clipboard history back out
is a remote control, and an environment-variable switch is not a boundary when
the attacker starts the process. `package.sh` refuses to build a DMG if the
symbol is found in the binary.

**Every assertion must be proved able to fail.** `qa-probe.py --prove` and
`security-probe.py --prove` run checks that MUST fail and stop if they pass. If
you add an assertion, break the code on purpose once and watch it go red. An
assertion that cannot fail is not evidence, and this suite has shipped two of
them: one flag that was set false in one place and never set anywhere else, and
one cache check that varied two inputs at once so the case it was testing could
never arise.

## Privacy and security

The short version: Clip stores everything you copy, in plain SQLite, on your
Mac. That file is the most sensitive thing on the machine, and it is treated
that way.

- **Nothing leaves your Mac** unless you turn on sync. No telemetry, no crash
  reporting, no analytics, no update check.
- **The store is owner-only**: `0600` on the database and its write-ahead log,
  `0700` on the directories. Repaired on every launch, so an older install that
  was created world-readable is fixed rather than left.
- **Confidential content is never recorded.** Concealed, transient and
  auto-generated pasteboard markers are all honoured, by default.
- **Secrets live in the Keychain** and are read only by the two pieces of code
  that need them. No API key, sync token or password reaches preferences, the
  settings sync payload, the export file or the logs.
- **No third-party code.** Nothing to audit, nothing to be compromised upstream.
- **The server trusts the token, not the caller.** Every row is scoped to a
  space id taken from the token and never from the request body, so naming
  someone else's space reaches nothing. Only `sha256(token)` is stored.
- **The app runs unsandboxed**, deliberately, and this is the honest trade: the
  global shortcut, reading the pasteboard and pasting into other apps all need
  it. The hardened runtime is on.

Full threat model and the evidence for each control: [SECURITY.md](SECURITY.md).

## The mark

Clip's mark is **⌘C** - the shortcut the whole app is about - in `#8ABDFF` on
black.

`brand/clip-mark.svg` is the trademark as drawn. `brand/clip-glyph.svg` is the
glyph alone, on no background, which is what everything else is built from:

```bash
swift brand/make-icons.swift brand/clip-glyph.svg <output-dir>
```

That writes every app-icon size and the menu-bar template from the one vector,
so the 16pt icon and the 1024pt one are the same drawing rather than the same
PNG resized. The app icon follows Apple's macOS grid - an 824/1024 rounded body
- and the menu-bar image is a template, so the system tints it to match the bar
rather than painting it brand blue against a white one.
