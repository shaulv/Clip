# Security

## What Clip holds

Every string its user has ever copied. In practice that set includes passwords
pasted from a password manager, API keys, session tokens, recovery codes,
private messages and card numbers. It also holds third-party AI provider keys, a
sync token, and it talks to a network service.

The blast radius of a mistake here is somebody's entire digital life. "It seems
fine" is not a standard this project accepts.

## Reporting a vulnerability

Open a private security advisory on the repository rather than a public issue.
Please include what an attacker gains and the smallest reproduction you have.
You will get an acknowledgement, and credit unless you would rather not.

## Threat model

Data flows: clipboard capture, the local database and media files, the Keychain,
AI provider requests, the sync service, Google sign-in, import and export, and
drag and drop.

Attackers considered: another process running as the same user; another user
account on the same Mac; someone on the network path; a malicious or compromised
sync server; a hostile file offered for import.

Explicitly **not** defended against: an attacker with root, or with your
unlocked Mac in front of them. Neither is defensible by an app.

## Controls

### Capture

**Confidential content is never recorded.** `org.nspasteboard.ConcealedType`,
`TransientType` and `AutoGeneratedType` are all honoured, on by default. This is
the convention password managers use to mark what they put on the pasteboard,
and a clipboard manager that ignores it quietly builds a plaintext archive of
its user's passwords.

Per-app exclusions are available for anything else you would rather it not see.

### At rest

The database, its write-ahead log and shared-memory file are `0600`; the support
and media directories are `0700`. Applied at launch, so an install created with
looser permissions is repaired rather than left, and applied again after SQLite
creates the WAL - which holds the most recent writes, meaning the most recent
things copied.

This was found wrong: the database was being created `0644` inside a `0755`
directory, readable by every process and every other account on the Mac.
Honouring the concealed flag counts for nothing if what *is* stored is
world-readable.

Clip does not encrypt the database. That would need a key, and a key an app can
use unattended is a key an attacker with the same file access can use too;
FileVault is the control that actually addresses this threat, and it is already
on the Mac. Saying so is more honest than a checkbox that implies more than it
delivers.

### Secrets

API keys, the sync token and the database password live in the **Keychain**, and
nowhere else. Verified by test: no secret reaches preferences, the settings-sync
payload, the export file, or the logs.

Reading a secret is an explicit call. `ServerConfig.load()` deliberately does not
fetch the password; `loadIncludingPassword()` exists for the two callers that
genuinely need it. Loading configuration should not be a way to end up holding a
password you had no use for.

### In transit and on the server

- HTTPS, with certificate validation left on.
- No credential in a URL or query string.
- **The space id comes from the token, never from the request body.** Naming
  someone else's space reaches nothing and deletes nothing. This is OWASP A01,
  and it is the most common real breach.
- Only `sha256(token)` is stored. The database alone syncs nothing.
- Every statement is parameterised.
- Request bodies are capped at 8 MB, refused on the declared length before the
  body is read.
- A space can be locked, after which no new device may claim its token.

### Google sign-in

- **No client secret in the app.** PKCE (S256), with a verifier generated per
  sign-in. The code is exchanged **by the server**, which holds the secret.
- Loopback redirect on an ephemeral port bound to `127.0.0.1` only, with a
  300-second deadline. Not a custom URL scheme, which any app can claim.
- `state` is checked on the way back.
- The identity token is verified for **signature** (against Google's live JWKS,
  with rotation handled), issuer, audience and expiry. `alg: none` is refused
  outright.
- The account is keyed on the subject, never the email, and an unverified email
  cannot key an account.
- Only `openid email profile` is requested. No Drive, no Gmail, no contacts.

### The shipped binary

The QA bridge - a file-driven harness that can drive the app and read its whole
history - is **compiled out of Release**. It exists only when `CLIP_TESTING` is
defined, which only the `Testing` configuration does. Gating it on an
environment variable would not be a boundary: whoever starts the process
controls the environment. `package.sh` refuses to build a DMG if the symbol is
found in the binary.

The hardened runtime is enabled. There are no third-party libraries, so there is
no supply chain to compromise.

### Sandboxing

Clip runs **unsandboxed**, deliberately. It needs the global shortcut, pasteboard
access and the ability to paste into other applications, and the App Sandbox
does not grant that combination. This is a real trade and it is stated rather
than buried: an unsandboxed app has the file access of the user running it.

The mitigations are that it links nothing third-party, makes no network request
you did not configure, and locks down everything it stores.

## Verifying any of this

```bash
python3 security-probe.py --prove   # the checks that must fail
python3 security-probe.py           # 45 checks with evidence (see docs/generate-counts.py)
```

Each check reports what it found, not merely pass or fail. If you do not believe
one, break the control it covers and watch it go red.
